# Changelog

All notable changes to GK Core Stuff are documented in this file.

## 1.04.000 (2026-11-06)

### Added

* Look External links with an icon after the link: in formatted text a link to another site is marked with a grey icon after the link text instead of Redmine's small image before it, as proposed for Redmine in Feature #44691; the icon never ends up alone on a new line, points outward in right to left languages and is not printed. A link to an e-mail address gets Redmine's e-mail icon in the same way. The look stands aside on a Redmine that has the change (GK Compat's ability `external_link_icon`).
* A scenario can set the looks and AM/PM on the same line it uses (`core_stuff: { looks: { <look>: off | optional | forced }, ampm: true }`), applied in the plugin's own scenario step; a key that is not a look, or another level, stops the scenario.
* Five values under External links shown as external, all on until switched off, choose where outside formatted text a link to another site also gets the look: custom fields of the format Link, Link values to URL, the project's homepage on its overview, and the links GK People and GK Icons mark. GK GUI Stuff draws the mark in those places; without it the values do nothing.
* Marks on the issue page's sections, for other plugins: the container of the description, the files, the subtasks and the related issues has `data-section` (`description`, `attachments`, `subtasks`, `relations`), and each one's heading has the class `section-heading`, so that a plugin finds a section by what it is and not by its heading's words or bold text. The files get a plain container of their own around their heading and list. Nothing changes on the page until a plugin reads the marks. Always on, listed with the hooks in core's views on the settings page, and it stands aside when GK Compat says the running Redmine has the marks.
* Marks on the pages: fixed classes and data attributes on parts of Redmine's pages that other plugins change, so that they find them without going by words, looks or place: `h1.site-title` in the header; `h2.issue-heading` and `h3.subject-heading` on the issue page; `th.current-status` and `td.current-status` in the workflow table's heading; `th.field-name` and `td.field-name` in the heading of the field permissions table; `data-report-column` (with `data-status-id` and `data-status-closed` on a status) on every heading, count and total of the detailed issue report; `data-attachment-id` on each row of an attachment list; `data-field` on the issue form's attribute rows, and on the Estimated time and % done rows of the issue bulk edit form; `scm_name`, `scm_command` and `scm_version` on the version control table's columns; `data-query-action` (`apply`, `clear`) on the query forms' buttons and `data-query-part="view-options"` around the Gantt chart's and the calendar's own controls; `data-menu-item="delete"` on Delete in the issue context menu; `data-section="attributes"` on the issue form's attributes box and the id `issue_description_edit_link` on the link that opens the description; `data-section-action="add"` on Add for subtasks and related issues; `data-form-action="save"` on Save in bulk editing and in every settings form. Always on; the marks do not show.
* More places for hooks: after the link to Redmine in the footer (`view_layouts_base_footer_powered_by_after`), after the author line on the issue page (`view_issues_show_author_after`), under a document's details (`view_documents_show_details_bottom`), beside Save in every settings form (`view_settings_form_save_after`, with the tab's name or the plugin; the API tab is `integrations` in every Redmine version, also where Redmine names it `api`), after the Information box on My account (`view_my_account_information_after`), before the issue list on its page, also above the no-data line (`view_issues_index_list_before`), and at the top of every issue list, on the issue list page and in the issue blocks of My page alike (`view_issues_list_before`). Always on; without a plugin that uses them the pages look as Redmine's.
* Marks on the links to people and groups: every link Redmine draws to a user or a group (`link_to_principal`, also through `link_to_user`) carries `data-principal-id` with the user's or group's id, so that a plugin knows whose name it is without going by the link's address. Where Redmine writes only the name there is no mark. Always on, shown on the settings page; nothing shows. It stands aside when GK Compat says the running Redmine has the mark.
* Marks in the header's project path: the root and ancestor project links of the project path at the top of the page carry `data-project` with the project's identifier, so that a plugin knows where a link leads without counting links and separators. Always on, shown on the settings page; nothing shows. It stands aside when GK Compat says the running Redmine has the mark.
* `GkCoreStuff.hook?(:hook_name, view: nil)`: whether the page being drawn calls a view hook, for other plugins that draw something on a hook when it is called and somewhere else only when it is not. Redmine's own hooks are called; a hook GK Core Stuff adds is called when Redmine has it, or when the views that call it come from GK Core Stuff's copies for the running Redmine version, and not when another plugin's own copy of such a view is used. `view:` asks about one of the views that call the hook. Decided by where the views come from, never by their text.
* Links and text in formatted text: one shared pass after Redmine has formatted a text (wiki pages, descriptions, notes, also in emails and exports), in which other plugins register a link processor, a text processor or both (`GkCoreStuff::FormattingProcessors.register`, or `formatting_processor` in a plugin's registration). A link processor gets each link with its address, its kind (external, e-mail, anchor or internal), whether it stands in code, and its attributes; a text processor gets each run of text outside code with whether it stands in a link, and may replace it. The text is read once for all plugins, after macros, headings and the table of contents, and is left exactly as Redmine wrote it when no plugin is registered or nothing changes. Always on; the settings page lists the plugins that registered. It stands aside when GK Compat says the running Redmine has the same registry.
* Links and text in formatted text: the links in a custom field's value (the format Link, and a link pattern on another format) go through the same pass after Redmine has formatted the value, given only to the link processors, with the custom value in the context (`origin` is `:custom_value`), so that a plugin marks those links without reading the finished value again. This part goes on running when GK Compat says the running Redmine has the registry for formatted text, until Redmine has the same for custom values; the registered plugins are kept for it and listed on the settings page.
* Marks in the issue reports: every count in the issue reports (Summary and the detailed table) is drawn inside a mark that says what it counts, `data-report-column` with `status`, `open`, `closed` or `total`, and on a status's count `data-status-id` and `data-status-closed`, so that a plugin knows a column by its mark and not by its place, its heading's words or a status's name. Nothing shows. Always on, shown on the settings page, and it stands aside when GK Compat says the running Redmine has such marks.
* Marks on the menus' links: every link Redmine draws in a menu (the top menu, the account menu, the project's tabs, the administration, also a child menu's links and its loose children) carries `data-menu` with the menu's name, so that a plugin knows which menu a link stands in without going by where it sits on the page. Always on, shown on the settings page; nothing shows. It stands aside when GK Compat says the running Redmine has the mark.
* The looks Badges in the middle of a list's row, The row's check box in the middle of the row, # before the issue number in lists, Menu icons in the row's colour and Equal margins in boxes without an icon say where they change the pages (their footprint in GK Records' register), shown as Affects on Administration, Appearance.
* Show has a picture for the check box in a list's row and for a form's row with only text, with the line through the middle of the text. The same line stands in the pictures of the status badges in a list and by a heading.

### Changed

* A new installation looks like Redmine: AM/PM on the same line as the time and every look are off until an administrator switches them on.
* Every look, % done as text, AM/PM on the same line as the time and Redmine's version in the footer are appearance settings in GK Records' register, set under Administration, Appearance (GK GUI Stuff) and kept in GK Records with every change as an event. % done as text, AM/PM and the version in the footer have only Off and Forced; % done as text keeps its four values under its setting. Without GK Records every one of them is off. A person's own choices about the optional looks are under My account, Appearance (GK GUI Stuff) and kept in GK Records; the box in Redmine's Preferences is gone. Levels, values and personal choices set before are not carried over. Show on the look Check boxes in alphabetical order lists three steps of how it works, and Show on Badges in the middle of a list's row and Badges level with the heading draws the badges off and on.
* The scenario step `core_stuff` sets the looks and AM/PM in GK Records' register, with the reason scenario.
* The settings page no longer has the box of the done ratio as text or the looks, with GK's recommendation and Like core; they are appearance settings on Administration, Appearance (GK GUI Stuff).
* External links: the link takes the colour role for external links (`--gk-role-link-external`, with a fallback so it works without GK GUI Stuff), a dotted underline, and the icon in the same colour. With GK GUI Stuff a link to the instance's own address is drawn as an internal link and the tooltip names the domain. The look is now called External links shown as external.
* Look Save instead of Submit: only the button that saves an issue's edit form and the two bulk edit forms (issues and time entries) gets Redmine's word for Save, the same three forms as the change proposed for Redmine. When issues are copied or moved in bulk, the Copy and Move buttons keep their words, as in the proposed change. The buttons are found by their forms, not by their word, so other Submit buttons (lost password, registration, forum reply, confirmations) keep their word, and the look keeps working when Redmine's word or the language changes.
* The settings about Redmine's badges say status badges.
* Texts say Redmine and Redmine's where they said core, core's or the Swedish word for it.
* The text on a progress bar and the plate behind it are colour roles, `--gk-role-core-stuff-progress-text` and `--gk-role-core-stuff-progress-plate`, so that a theme can set them; without them the colours are as before.

### Fixed

* % done as text: the help under Position says what the four positions do.
* The user's edit page writes its heading with the avatar before the login as markup and calls the hook after the title itself, instead of inserting the avatar at a space in the finished title, which could break the page if the title's markup changed.
* AM/PM on the same line as the time: the no-break space is put into the time format before AM/PM, as in the change proposed for Redmine, instead of being searched for in the formatted time by the words of the language's AM and PM, so it no longer depends on those words.
* Look Check boxes in alphabetical order: a tracker's custom fields are found by the name Redmine gives their check boxes, and the list keeps Redmine's order when its markup is not one box per item, instead of sorting by the nearest paragraph and its labels, which could reorder the wrong block.
* Look Check boxes in alphabetical order: the projects of a tracker and of a custom field are found by the classes Redmine gives its nested project list (`ul.projects`, `li.root` and `li.child`, `div.root` and `div.child`), not by which element stands directly inside which.
* % done as text: Redmine's empty legend under the bar is hidden by its own class inside the bar with text, instead of being cut out of Redmine's markup by a pattern, which left an empty line under every bar when the markup differed.
* Redmine's version in the footer: the version is drawn by the server on the hook right after the link to Redmine (`view_layouts_base_footer_powered_by_after`), instead of a script looking for a link in the footer, so it no longer depends on JavaScript or on the links that stand in the footer. Where another plugin draws its own page frame instead of Redmine's, the version is not shown.
* Look The repositories table as a list: the version column is known by its class `scm_version`, not as the last column, so a column added or moved no longer gets its width.
* Look Headings like their columns: a column is known by the class Redmine gives both its heading and its cells in the query lists, not by its place in the row, and a column of texts by Redmine's classes for descriptions, notes, comments and text custom fields, not by the length of its texts in the current language. A list whose headings have no class keeps Redmine's centred headings.
* Look Buttons and fields of one height: the controls evened out are those of one form standing side by side on one line, as the browser shows them, not those that happen to share a parent element.
* Look Equal widths for fields under each other: the fields are those of one form and fieldset standing alone on their lines at the same start edge, as the browser shows them (a field further off on the same line stands in another column, so each column of the two-column issue form is evened on its own), and a table's column is the cells starting at the same edge, not paragraphs found by walking from one to the next or a cell's number; fields in a part opened by a click are measured then.
* Look Badges level with the heading: the badges are known by Redmine's classes for the issue's status and Private on the issue page, not by standing after the heading. A plugin's own page built like an issue's opts in with the class `gk-heading-badge` on its badge.
* Look # before the issue number in lists: the link in the id cell is found however Redmine wraps it.
* Look Equal margins in boxes without an icon: the box no longer asks whether an icon stands directly inside it; Redmine draws no icon in the space of a warning or a "no data" box.
* Look Move handles in the icons' colour: the space goes on the group of icons that does not hold the move handle, not on the second group in order.
* Every look now says where it changes the pages, so the band and panel after a save count real places instead of 0 for looks such as External links, % done as text and Save instead of Submit.
* The Save button in the issue's edit form is counted as a place as soon as the form is opened.
* AM/PM on the same line as the time states in its help text that the change has no element of its own, so no places are counted for it.
* The Swedish name of the setting says "% Klart", as Redmine does.
* The plate behind the text on a progress bar lies only behind the text and no longer covers the whole bar. The text stays in the bar's middle.
* A look's row that is off no longer loads its stylesheet on Administration, Appearance for its picture under Show. The picture has its own rule, held to its own row, and the look's stylesheet comes only with the row on.

## 1.03.000 (2026-10-28)

### Added

* Look Menu icons in the row's colour: in a menu (a button row's and a note's ..., the issue list's right click) the icon of the row under the pointer keeps the row's colour, as its text does, instead of turning red as the icon of an ordinary link does (Redmine 6.1 and later; 6.0 already does so).

## 1.02.000 (2026-10-28)

### Added

* Hooks in Redmine's views for other plugins, in four modules that are always on and stand aside when Redmine has the hooks itself: the page's frame (the top and bottom of the header and the footer, the top of the content and the sidebar, after the page title, around the issue on the issue page), the button row and the menus (a hook in the button row of sixteen pages and the actions menu of eight, and menus that plugins add items to for an issue, the issue list's context menu, a project, a user and a version), the forms (the top and bottom of seven forms and after sections of the issue and user forms) and the lists (a row's classes and content after the row in the issue, project and user lists). The views are Redmine's own with the hooks added, one copy per supported Redmine series; where another plugin already overrides one of them, that plugin's view is used. The settings page lists the four with their views and the hooks in use.

## 1.01.000 (2026-10-27)

### Added

* A plugin can register how its lines in an issue's history are drawn for every key that matches a pattern, not only for one key.

### Changed

* This version is installed anew and does not upgrade an earlier one: uninstall the earlier version first (migrate it down to 0 while its own files are in place), then install this one. Nothing is carried over from the earlier installation.
* The registers for tabs and for history lines are two modules instead of one, so that each stands aside by itself the day Redmine has it. Both are always on and can no longer be switched off, since other GK plugins require them for their tabs and history lines. The settings page shows each as a locked box with what is registered in it; the history lines registered are now listed too.
* The export log and the file names of Redmine's exports have moved to the plugins they always needed: the log of exports, downloads and prints is part of GK Records 1.04.000, and the names from the rule for file names are part of GK Revisions 1.00.000. GK Core Stuff keeps the list of which of Redmine's actions send an export, which both read; without those plugins the two did nothing here either.
* Whether Redmine itself already has what a module adds is asked of GK Compat 1.01.000 or later instead of looked for in Redmine's classes and settings. Without GK Compat, or with an older one, every module hooks in as before.
* Uninstalling (migrating the plugin down to 0) takes the plugin's keys out of the users' preferences in the migration itself, without calling the plugin's own code.
